# Local native enrollment integration and dependency boundary

This isolated follow-up preserves the separately reviewed four-file JavaScript enrollment slice unchanged. It is local preparation: no HTTP consent endpoint, runtime file/environment option, live credential, provisioning action or deployment is added. The new native gate builder, fields and route branch are compiled only under `cfg(test)` and remain crate-private. Even test builds require an HTTP IPv4 loopback origin and development mode. Normal and release builds have no gate selector. Ordinary native configuration retains its prior behavior; no production enablement is implied.

The crate is not a published SDK (`publish = false`). Public Rust policy helpers exist for internal server composition and integration qualification; they are not a model tool or HTTP enrollment interface. Code holding an `App` and choosing server trust pins is trusted server code. A future embedding that exposes these helpers must derive pins from server state and authenticate the owner; accepting pins from a request would violate this API contract and needs separate review.

## Reused shared dependency

The EXP-711 owner supplied an uncommitted snapshot of `agent_endorsement.rs` and `xrpc/agent_binding.rs`, with exact hashes in `review-records/exp-710-native-enrollment-dependency-overlay.json` outside this worktree. These are byte-exact qualification dependencies owned by EXP-711. Support changes are its `sync::record_proof` extraction and `pub mod agent_binding`. No provisioning, dispatch or MCP module was copied. Delivery must reconcile this shared change rather than ship another verifier.

`verify_pair` remains the CAR/signature/MST verifier. The hosted `agent_binding::observe` reads a principal repo on the serving shard. EXP-710's fixed remote path does not call it. Instead, `agent_endorsement_fetch::observe_fixed` retains fixed HTTPS origins, pair/service pins, bounded reads, fresh DID rereads and current-head checks, returning the shared observation type. A missing alias requires a stable second agent DID read. The legacy `resolve_fixed` JSON statuses and error behavior are retained; failure becomes `Unavailable` only at the typed sibling. Observation resolution start time conservatively bounds local evidence age; it is not a global freshness or authorization lease.

## Authenticated consent writer

`agent_enrollment::apply_owner_consent` is an internal storage API, not a route. It authenticates the supplied bearer with the existing `authenticate` extractor and requires a full active account session for the configured owner. App passwords, service identities and other owners cannot substitute. Owner and allowed agent/caller pairs are server trust pins, never enrollment request fields. Enable requires an already active account on this PDS/cluster; no account, key, membership or credential is provisioned. Consent alone is not evidence of endorsement and grants no admission until the separate proof gate succeeds.

One owner-routed private CAS row holds pair state, monotonic revision, decision receipts and a one-way owner shutoff. Request ID plus semantic digest fences changed retries. An identical retry returns its original receipt and current effective state without writing; an old enable cannot restore a disabled or revoked agent. New operations require the current owner revision, so disable winning a CAS race fences a delayed enable. Per-agent disable allows a separately authenticated fresh enable; endorsement revocation and owner shutdown have no automatic restoration operation. Other owners' partitions are independent.

The journal retains at most 64 ordinary operation receipts and bounds bytes and allowlist size. Exhaustion refuses new ordinary operations but reserves the separate owner-shutdown slot, and reserves 1 KiB of byte capacity for it, so shutdown remains available at receipt/byte capacity and after restart. Authenticated owner shutdown also remains available if the configured agent allowlist is empty; it never selects an agent or grants access. Retention, key rotation, restoration and operator recovery need a reviewed design; deleting state is not a recovery strategy. All writers of this namespace must use private CAS. Account inactivity and unavailable/malformed state deny admission.

## Native cache/dispatch boundary

`agent_admission::run_if_admitted` accepts a service token, server-configured caller and action callback. It uses existing `verify_agent_contact_jwt`, accepting no request-supplied proof or consent boolean. It reads consent for the fixed owner/agent, verifies current typed identity evidence, then revalidates the token and rereads policy. `Verified` is required; signed absence, undeclared identity, unavailable evidence, wrong pair, future timestamps and observations older than five seconds deny admission. Disable, endorsement revocation, owner shutdown, deletion or any policy revision change during proof verification denies the action. Proof age is checked again after the final policy read.

A process-local single-operation permit bounds proof/decision concurrency for this fixed pair. Concurrent requests are refused without queuing or starting another observer; completion or cancellation releases the permit. This does not skip current-proof checks for cached retries.

In the compile-time-only explicit loopback mode, the actual native handler invokes this wrapper before the entire existing decision block, including returning a cached reply. A disposable fixture seeds a real cached decision: the legacy route can return it, while the gated route refuses missing consent, disable and owner shutoff. The fixture never sends a request while an enabled consent row could invoke the fixed public proof fetch. Synthetic gate tests exercise positive verified proof and unavailable/revoked evidence without live networking. Those denial-only cases are now supplemented by the mounted signed-authority fixture below.

The gate does not replace signed Card, active-agent, endpoint, quota, retry or private profile provenance checks. Fresh legacy decisions still perform their existing identity evaluation after admission; no stronger freshness or cancellation guarantee is claimed. Revocation after the final admission read can race already-admitted work. The JavaScript fixture is not a source of production Ed25519 keys, HTTP signatures, OAuth claims or native rows.

## Compile-time-only mounted authority qualification

An in-crate `cfg(test)` harness mounts the actual native router on a development loopback listener. Its task-scoped byte transport serves synthetic DID documents, independent record/head reads and a signed repository CAR for the unchanged fixed requests. The same response-origin, media, redirect, encoding, length and streamed-size checks and the shared Rust verifier remain in use. Both `observe_fixed` and the legacy fresh evaluation use this transport. Normal library builds contain no fixture module or selector, and retain guarded HTTPS only. There is no environment, file, URL or request override. The fixture harness explicitly denies real HTTPS in its own task context, while each mounted request receives a scoped synthetic authority. Unscoped harness reads fail closed; unrelated parallel tasks are unaffected. There is no process-global fixture selector.

Disposable issuer tokens drive actual caller and principal-session authentication, followed by the consent CAS writer. A loopback Node stub reuses the HMAC profile bridge and reports only actual dispatch counts. The first mounted request must return a verified result; the identical retry must return the same result and leave the total actual stub dispatch count at one, while performing a new admission-proof read. The harness independently verifies signed absence, then requires cached and fresh requests to fail for absence, unavailable authority, tampered proof, wrong pair, changed head/DID data, bad media, redirects, oversized bodies and encoded responses. It also exercises disable during a paused proof, fixed fetch timeout, cancellation, local revocation and owner shutoff, with no additional bridge dispatch.

Owned process, counter-reader and route-server cleanup are checked. Failed startup has an owned child guard, and timed-out server cleanup aborts and reaps the owned task. These are synthetic authority and profile assertions, not live identity control, Kody execution, production signed-Card qualification or production enablement.
